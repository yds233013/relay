# 0004: Persistence, imports, pipeline runs and audit (M3)

Status: **Accepted** (autonomous Tier 1 and Tier 2 decisions, 2026-09-17).

These decisions refine [data-model.md](../data-model.md), [architecture.md](../architecture.md) and [governance.md](../governance.md). Where they differ from those documents, this record wins until the documents are updated.

## Decisions

| # | Decision | Why |
|---|---|---|
| P-01 | **Staged records use one semi-typed table** (`staged_records`). The columns used for filtering and drill-down are typed and indexed (record type, natural key, account, party, document, entry, date, period, functional amount, source import, row, lines). The canonical record itself is stored as JSON. | Fewer tables to keep in sync with the canonical model. Drill-down queries need only the typed columns. The data model's per-type tables can be introduced later without changing the API. |
| P-02 | **The engine reads the verified bytes of each dataset's active import**, not `source_rows`. Blob reads re-hash the content. `source_rows` are written by the same CSV reader, so staged-record lineage (import, row number, physical lines) points at rows the API serves. | One parsing code path, and the engine stays pure. The run fingerprint includes the file hashes, so the bytes are exactly what was imported. |
| P-03 | **Database-side code lives in separate packages** from the pure readers: `relay.imports` next to `relay.ingestion`, `relay.mapping_sets` next to `relay.mapping`. Policy versions belong to `relay.workspace`. Import-linter enforces the layers api > worker > pipeline > changes/issues > mapping_sets > imports > workspace/identity/jobs > audit > engine > ingestion/mapping/profiling > canonical > core. | Keeps the engine purity contract and avoids package cycles. |
| P-04 | **The run fingerprint** hashes the migration id, conversion plan, active import hashes, approved mapping set ids, required dataset types, policy version, overlay identity, the engine input fingerprint, and the engine, rule, reconciliation and gate versions. | architecture.md §4.1, plus required datasets because they change G1. |
| P-05 | **Run requests are idempotent**: under a per-migration advisory lock, a queued, running or succeeded run with the same fingerprint is returned. Partial unique indexes back this up. If the configuration changes between request and execution, the run fails with `pipeline.inputs_changed` instead of running on different inputs. | architecture.md §4.1. A run's results always match its fingerprint. |
| P-06 | **A run executes in one transaction**: staged records, findings, reconciliations, candidates, issue synchronization, readiness and the `succeeded` status commit together. A failure rolls everything back, and the failure is recorded in a separate transaction. Bulk rows are written with PostgreSQL `COPY`; amounts are validated with `validate_amount` first. | No partial results are ever visible. Measured on Brightwater: persistence went from 10.1 s with multi-row inserts to 1.5 s with `COPY`. |
| P-07 | **Uploads are request bodies** (`text/csv`, file name in `X-Relay-Filename`), not multipart forms. The body is read in chunks and refused once it exceeds the limit. The declared `Content-Length` is checked first. | No new dependency. The size limit applies before the file is stored. The whole body (at most `RELAY_MAX_UPLOAD_BYTES`) is held in memory while it is spooled; true streaming to disk from the async endpoint is a later improvement. |
| P-08 | **Encoding is sniffed deterministically**: a UTF-8 BOM gives `utf-8-sig`, valid UTF-8 gives `utf-8`, anything else is decoded as Windows-1252. The delimiter is the most frequent of `,` `;` tab `|` in the header line. Both are recorded on the import and used by the engine. | architecture.md §5.1. |
| P-09 | **Profiles store shape only** (blank and distinct counts, pattern counts, ambiguous MM/DD dates), never sample values. Profiling runs inside the parse job. | SEC-21. A separate profile job added no value at this size. |
| P-10 | **Stored files are deduplicated by content across datasets.** An import is idempotent per (dataset, file). | data-model.md §5. |
| P-11 | **Change request core only**: draft, submit (with required approvals, before/after and base entity versions), review (segregation of duties in the service and in a database trigger), and approve-and-apply in one transaction. Only the `column_mapping_set` kind has an applier. Other kinds raise `NotImplementedError` until their milestone. A stale change request is **recorded and returned, not raised**, so the marking is not rolled back. | The day-9 seed approves mappings through recorded change requests, as planned. Staleness is audit evidence. |
| P-12 | **Account mapping is still an imported dataset** (the implementation team's file) in M3. `account_mapping_set_approved` is reported as true for G3. Governed account mapping sets arrive with the change request kinds in M5. | Keeps M3 to persistence without inventing a second account mapping path. |
| P-13 | **No overlay tables yet.** Runs use empty overlays until record overrides, entity decisions, dispositions, waivers and sign-offs arrive with their change request kinds (M5–M7). | Avoids tables nothing can write to. |
| P-14 | **Readiness is evaluated once per run**, with pending change requests counted at that moment. The API marks readiness `stale` when the current fingerprint differs from the run's fingerprint. Re-evaluating readiness when governance state changes without a new run is M7. | FC-14. |
| P-15 | **Development identity** is the `X-Relay-User` header naming a seeded user. It is on by default in local and test, off otherwise, and refused at startup if enabled in production. Assuming an identity is not audited per request. | SEC-11. A per-request audit event would flood the migration chain; the governed actions themselves are audited. |
| P-16 | **Audit chains**: each migration has its own chain and platform events (users, companies) form a separate one. `migration_seq` is assigned under a transaction-scoped advisory lock. The hash covers every stored field, with timestamps in canonical RFC 3339 form. Tampering by a database owner who disables the append-only trigger is detected by `relay verify-audit`. | GV-06. Tamper-evident, not tamper-proof, as documented. |
| P-17 | **Stage timings are integer milliseconds.** | The FC-01 float guard now also covers the engine, imports, mapping sets and ingestion. It flagged float timings. The single exemption is entity string similarity (`difflib` ratios are not amounts). |
| P-18 | **Job heartbeats are not refreshed during a handler.** A job running longer than 10 minutes can be requeued by another worker. Handlers are idempotent (status checks under row locks), so a duplicate execution returns without writing. | Brightwater runs take about 3 s. Heartbeating long runs is needed before the 250k-line scale is run through the worker. |

## Mismatches found and fixed while building M3

- `rule_exceptions.expected` and `observed` were generated `NOT NULL` from `Mapped[Any]`. `COPY` exposed it on the first persisted run. Fixed in the model and the revision, which had not been committed yet.
- The `unassigned` party drill-down listed every party's open invoices. Open items and aging items always have a party, so the drill-down now shows the opening control balance not explained by the opening aging instead (SC-04).
- Integration tests used a separate blob directory per test, while stored files are deduplicated across the database. A missing blob now raises `storage.integrity_failure` instead of a bare `FileNotFoundError`.
- Seeding from the host into a database served by the Compose worker failed: the worker claimed the parse jobs but could not see blobs stored on the host. Three fixes followed. A parse job that fails permanently now marks its import `failed` (audited) instead of leaving it `pending`. An upload whose content is already known but whose blob is missing from this store restores the blob from the verified upload bytes. `make demo-seed` runs inside Compose, sharing the worker's blob volume (`make demo-seed-host` remains for host-only setups).
- A job with a malformed payload crashed the worker while it recorded the failure. The worker now records the failure and continues.
- `docker compose up --wait` requires every service to report health. The worker touches a heartbeat file on every loop iteration, and its healthcheck checks that the file is recent.

## Verification

- The persisted Run #1, rebuilt only from database rows, matches the golden manifest: 89 of 89 comparisons.
- Persisted gates fail exactly G1, G3, G5–G10 and G12. There are 65 open issues with unique keys.
- The R3 drill-down for `C-0233` shows `INV-10877` as `left_only`. Its ledger record's lineage resolves to the GL export row with `Num = JE-AR-10877`.
- Both the migration and platform audit chains verify after seeding. A tampered event is reported at its exact sequence number.
- Append-only triggers reject UPDATE, DELETE and TRUNCATE on source rows, quarantined rows and audit events. The self-approval trigger fires. Competing workers never claim the same job. Duplicate uploads and duplicate run requests are idempotent.
