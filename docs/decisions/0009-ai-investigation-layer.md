# 0009: AI investigation layer (M8)

Status: **Accepted** (autonomous Tier 1 and Tier 2 decisions, 2026-09-17).

| # | Decision | Why |
|---|---|---|
| A-01 | **Two packages.** `relay.ai` holds providers, tools, the investigator loop, prompts, redaction, the findings schema and provenance verification; it imports only `*.read_model`, `*.schemas` and pure modules (import-linter forbidden contract with indirect imports allowed, plus a contract that read models never import write paths). `relay.investigations` owns the tables, the read-only session, consent and rate checks, persistence of steps and findings, review, and drafting change requests. | ai-safety.md §2 puts transcript persistence under `ai/`, but CLAUDE.md forbids `ai` from importing models or services. The persistence layer sits above `ai` so the boundary stays mechanical. |
| A-02 | **Findings arrive through a terminal `submit_findings` tool** whose input schema is `FindingsSubmission`, not a separate `final_output_schema` provider argument. Invalid submissions are returned to the model as tool errors. If the model ends without submitting, it is reminded once, then the investigation fails. | One mechanism for structured output across providers; the scripted and live paths are identical. |
| A-03 | **The Anthropic provider uses the standard library** (`urllib`, HTTPS enforced, injectable transport for tests) against the Messages API with `x-api-key` and `anthropic-version: 2023-06-01`. No SDK dependency. `temperature` is not sent (current documentation marks it deprecated). Retries on 429/5xx with jittered backoff within the turn's timeout (bounded by the remaining investigation time). The key is a `SecretStr`, used only in the request header, never logged or returned. | Resource discipline (no new dependency); vendor types never leave the module. Default model `claude-opus-5`, configurable with `RELAY_AI_MODEL`. |
| A-04 | **Tool sessions are `SET TRANSACTION READ ONLY` with a 5 s statement timeout**, and `migration_id`/`run_id` are bound in `ToolContext` from the investigation's pinned run (the latest succeeded run when it started). An integration test runs every tool in that session and checks that a write raises in PostgreSQL. | ai-safety.md §3.2. |
| A-05 | **Tool results are redacted, truncated to 20 KB, and wrapped** as `<tool-result step=".." untrusted-data="true" truncated="..">`. Redaction: tax and bank identifiers to the last four characters, emails to the domain, long digit runs masked, free text truncated to 200 characters. Verification checks against the full redacted result. The persisted step stores what the model saw, plus the SHA-256 of the full result. | ai-safety.md §3.1 and §6. |
| A-06 | **Provenance verification** implements ai-safety.md §4.3 checks 1–5, with check 5 (suggested action references exist in the pinned run) through `RunReferences` over read models. Numbers are compared as decimals after removing grouping separators (parenthesised negatives accepted), so `-29,060.00` equals `-29060`. | Deterministic, server-side. |
| A-07 | **`requires_approval` and `draftable` are computed by the server.** `draftable` means that no change request was drafted yet and `promotion_problem` returns nothing: not failed, not dismissed, requires approval, and the action type has a drafter (`change_account_mapping`, `record_override`, `entity_decision`, `disposition`). `request_reimport` requires approval but is carried out by people (a new upload), so it is not draftable. Failed findings cannot be accepted either. | ai-safety.md §4.4; the UI hides buttons from server fields, and the API refuses regardless (409 `ai.finding_not_promotable`). |
| A-08 | **Drafts are owned by the operator**: `origin=ai_finding`, `origin_finding_id`, `evidence_refs` from the finding, requested by the person who clicked. They follow normal submission and approval. The operator needs the change-request permission (viewer gets 403). Audited `finding.drafted_change_request`. | AI is never a requester or reviewer. |
| A-09 | **Consent is a `policy_change` with `ai_enabled`**, stored on the migration and approved like any other policy change. It does not change the run fingerprint or request a run. AI is available only when a provider is configured **and** the migration consented. | ai-safety.md §6. Consent is governance, not input data. |
| A-10 | **Investigations are jobs** (`run_investigation`), started by `POST /migrations/{id}/investigations` (202), at most 20 per person per hour. | Keeps model latency out of requests; bounds cost. |
| A-11 | **Mapping suggestion tasks were not built** (ai-safety.md §5). | Implementation plan cut line 2 ("keep the investigator"). Deterministic column suggestions from M5 remain. |
| A-12 | **UI**: an Investigate panel on the overview and issue detail renders only when `/ai/status` says available. The investigation page shows the AI label, findings with verification badges, per-evidence check results and problems, review (accept/dismiss), and draft buttons from `draftable`, plus a plain-text step transcript. Failed findings are collapsed behind a warning. All AI output goes through `components/ai-finding.tsx`. | CLAUDE.md and ai-safety.md §6 (output injection, over-trust). |

## Found while building M8

- The forbidden-import contract first flagged `relay.ai` for indirect imports of `relay.core.db` through read models. Indirect imports are now allowed in that contract, and a separate contract keeps read models from importing write paths.
- The scripted E3 case needed the issue selected by all of its subjects, because the duplicate-candidate rule produces one issue per pair.
- In `next dev`, a form submitted before hydration sends `Origin: null` (the app sets `Referrer-Policy: no-referrer`), and Next.js rejects the Server Action. The production build (used by the stack and E2E) is not affected. This was observed during manual testing of the investigation flow against a scratch stack.

## Known limitations

- **No live eval run has been recorded**: no provider key was available. The acceptance item "live eval run recorded: E1–E5 root cause hit, 0 fabricated references, E4 injection compliance 0" is **not met**. Scripted transcripts pass (5/5 root cause, 0 fabricated, 0 injection violations, and the hallucinating control fails verification), but they test the harness, tools and verifier, not a model.
- `sent_fields` records each tool call's name and argument names, not a field-level inventory of the data returned to the provider.
- Token budgets rely on the provider's reported usage; the scripted provider reports zero.
- An investigation pins the latest succeeded run. It is not re-pinned, and nothing marks it as stale when a newer run exists.
